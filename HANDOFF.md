# HANDOFF — FieldOps

Документ для разработчика или ИИ-агента, который продолжает проект. Прочитайте его целиком перед правками (около 5 минут). Пользовательское описание и развёртывание — в [README.md](README.md).

## 1. Что это и в каком состоянии

**Боевая система** (не учебная) для компании, которая обслуживает объекты (камеры, терминалы, сети) в Казахстане и соседних странах. Спецификация — ТЗ «Система заявок и отчётов о выездах» (PDF у заказчика; ключевые требования пересказаны ниже). Прототип заказчика на Google Apps Script лежит в `Прототип/` — только как референс поведения, стек не повторяем.

Три страницы с общей БД:
1. **Подача заявки** `/tickets/new` — диспетчер/руководитель. Номер по городу: `AST-0001`.
2. **Список и карточка** `/tickets`, `/tickets/[number]` — в карточке блок «Завершение работ» со всеми отчётами (фото, видео, карта геометок, устройства).
3. **Отчёт о выезде** `/report` — выездной сотрудник с телефона, работает без связи.

**Статус на 15.10.2026:** MVP (этап 1 ТЗ) написан и проверен локально. **Не развёрнут** — нет доступов к Yandex Cloud, домена и OAuth-ключей. Docker-образ ни разу не собирался (на машине разработки нет Docker). На реальных телефонах не проверялся — только в эмуляции Chrome.

## 2. Решения заказчика (переопределяют ТЗ)

Ответы на открытые вопросы раздела 13.1 ТЗ:
- Заявки создают **только диспетчер и руководитель**; выездной сотрудник — нет (проверяется на сервере, `can.createTicket`).
- Внешних заказчиков (без корпоративной почты) — **нет**.
- **Уведомления не делаем вообще** (ни почта, ни Telegram, ни push).
- Подписи на экране — **нет**.
- Данные и файлы — **в Yandex Cloud** (Managed PostgreSQL + Object Storage).
- Данные из прототипа **не переносить** (только справочники городов и объектов — уже в `data/seed.json`).
- **Реестр устройств по объектам (ТЗ 8.3) нужен в MVP** — сделан.
- Стек выбран разработчиком, согласовывать не нужно.
- Позже по просьбе заказчика: **адрес в заявке и в отчёте — необязательное поле.**

Решения, принятые по ходу (ТЗ не уточняло):
- Роли «руководитель» и «администратор» — одна роль `manager`.
- Заявки не удаляются никогда, только отменяются.
- Если сотрудник отчитался по неназначенной заявке (или нажал «Я на объекте»), он становится исполнителем.
- Выездной видит: назначенные ему + неназначенные открытые + заявки, где у него есть отчёт.
- Новый город — только через справочник (не из формы заявки). Новый объект — можно вписать прямо в форме.

## 3. Стек

Next.js 16 (App Router, Turbopack) + React 19 + TypeScript · PostgreSQL + Drizzle ORM · Tailwind CSS v4 · zod 4 · arctic (OAuth Google и Яндекс ID) · AWS SDK v3 (S3 = Yandex Object Storage) · idb (IndexedDB) · esbuild (сборка service worker) · exceljs · pdfkit · sharp · Leaflet + OpenStreetMap · vitest · Playwright.

**Внимание: Next.js 16 отличается от того, что вы знаете** (async `params`/`cookies()`, `proxy.ts` вместо `middleware.ts` и т. д.). Перед правками сверяйтесь с `node_modules/next/dist/docs/`. Middleware/proxy в проекте не используется — права проверяются в страницах (`requireUser`) и в API-обёртке (`api()`).

## 5. Инварианты — не ломать

1. **Нумерация заявок** — `nextTicketNumber()` в `tickets.ts`: `UPDATE cities SET last_number = last_number + 1 RETURNING` **в той же транзакции**, что и вставка заявки. Номер никогда не переиспользуется. Код города нельзя менять после первой заявки (`admin.ts`). Тест: 20 параллельных заявок в `tests/smoke.mjs`.
2. **Отчёт неизменяем.** Нет API для правки или удаления. Руководитель только комментирует (`report_comments`).
3. **Идемпотентность.** ID отчёта генерирует телефон (`newReportId()`); повтор `POST /api/reports` с тем же ID возвращает `duplicate: true`. Файлы имеют UUID с телефона; повтор частей и `complete` безопасен.
4. **ФИО и почта — из сессии**, а не из формы. В отчёте хранятся снимки (имя, город, объект, адрес на момент отправки).
5. **Статус заявки по отчёту** — `WORK_TO_TICKET` в `shared/constants.ts`: full → done, partial → in_progress, revisit → revisit. Отчёт по закрытой или отменённой заявке — 409. Каждая смена статуса пишется в `ticket_events`.
6. **Права проверяются на сервере** (`can.*`, `visibleTicketsWhere`). UI только прячет кнопки. Критерий ТЗ: выездной не может обойти права прямым запросом к API — это проверяет smoke-тест.
7. **Реестр устройств** (`applyRegistry` в `reports.ts`) управляется полем `kind` у действия (install / configure / replace / dismantle / check / other), а **не названием** — названия действий редактируются в справочнике. Один активный IP на объект (частичный уникальный индекс).
8. **Файлы не публичные.** Только `/api/files/[id]` с проверкой доступа к заявке.
9. **Время в UTC**, показ в поясе браузера (cookie `tz`), формат `дд.мм.гггг чч:мм` (`shared/format.ts`). Плановая дата — `date` без времени.
10. Справочники **не удаляются, только деактивируются** (`active = false`).

## 6. Как работает офлайн (самое хрупкое место)

- Черновик отчёта и выбранные фото и видео сразу пишутся в IndexedDB (`kv` + `blobs`); при перезагрузке восстанавливаются.
- «Отправить» → черновик переносится в `outbox`, форма очищается. `processOutbox()` сначала грузит файлы частями по 5 МБ (`/api/uploads/...`), затем `POST /api/reports`.
- Нет сети → элемент остаётся `queued`. Повторы запускаются при событии `online`, раз в 30 с, при открытии страницы и через **Background Sync** в service worker (Android/Chrome; на iOS — только при следующем открытии).
- Web Locks (`navigator.locks`) не дают странице и SW отправлять одновременно.
- Ошибка 4xx (валидация, закрытая заявка) → `error` с `fatal: true`; пользователь жмёт «Исправить» и отчёт возвращается в форму.
- SW кэширует HTML страниц (network-first, ключ без query) и `/_next/static` (cache-first). `/api/*` не кэшируется. Справочники для офлайна лежат в IndexedDB (`refs:<userId>`).
- **SW регистрируется только в production-сборке** (`ClientBoot.tsx`). В dev офлайн-загрузка страницы не работает — это нормально.
- Геолокация и SW требуют HTTPS (кроме `localhost`). С телефона по `http://192.168...` геометка будет «не получена».

## 7. Запуск и проверки (Windows, без Docker)

```bash
npm install
# .env.local: скопировать из .env.example; DEV_LOGIN=true, SEED_ADMIN_EMAIL=...
npm run db:local          # отдельное окно; embedded PostgreSQL :54329, данные в .data/pg
npm run db:migrate && npm run db:seed
npm run dev               # http://localhost:3000; с телефона: next dev -H 0.0.0.0 и APP_URL=http://<LAN-IP>:3000
```

Вход в dev: на `/login` блок «Режим разработки» (выбрать сотрудника). Он работает только при `DEV_LOGIN=true` и **не в production**.

Проверки (запускать после изменений):
```bash
npm run typecheck && npm run lint && npm test
node tests/smoke.mjs                       # 19 сценариев API по критериям приёмки; нужен dev-сервер с DEV_LOGIN
node tests/e2e-report.mjs                  # Playwright: форма отчёта, черновик, офлайн-очередь (PW_CHANNEL=chrome — системный Chrome)
node tests/e2e-offline.mjs http://localhost:3001   # PWA без сети; нужна production-сборка на :3001
```

Smoke- и e2e-тесты **создают данные** (заявки, сотрудники disp@/field1@/field2@example.com). Не запускайте их против боевой БД.

Схема БД: правите `schema.ts` → `npm run db:generate` → новая миграция в `drizzle/` → `npm run db:migrate`. Старые миграции не редактировать.

## 8. Подводные камни

- **Tailwind v4:** `@apply` своих классов не работает. Классы `.btn-*`, `.input`, `.card` описаны в `globals.css` через встроенные утилиты.
- **eslint `react-hooks`** (новые правила): нельзя синхронно вызывать `setState` в `useEffect` и объявлять компоненты внутри рендера. Используется приём «состояние с ключом» (см. `registryState`, `dupState`).
- Функции нельзя передавать из серверных компонентов в клиентские — поэтому колонки справочников описаны в `admin/tabs.tsx` (client).
- **Git Bash на Windows портит кириллицу в аргументах curl** — API-проверки пишите на Node (`fetch`).
- `npm install` с npm 11 блокирует install-скрипты; разрешённые перечислены в `package.json → allowScripts`.
- `next dev` сам дописывает блок в `AGENTS.md` — это нормально, коммитьте его.
- `.env.local` на машине автора: `APP_URL=http://192.168.0.115:3000` (для теста с телефона). Это локальная настройка, в git не попадает.
- PDF использует шрифт DejaVu из `assets/fonts` (кириллица). `output: standalone` копирует его через `outputFileTracingIncludes`.

## 9. Что не сделано / следующие шаги

**Для запуска в работу (блокеры):**
1. Получить от заказчика: домен, доступ к Yandex Cloud, тип корпоративной почты (Google Workspace или Яндекс 360) и домен почты → настроить OAuth (README, раздел «Развёртывание»).
2. Собрать Docker-образ, развернуть (`docker compose up -d --build` с `RUN_SEED=true` в первый раз), завести сотрудников (`/admin?tab=employees` или импорт из Excel).
3. Пройти критерии приёмки (раздел 12 ТЗ) на **реальных** Android и iPhone по HTTPS.

**Риски, требующие проверки:**
- iOS 15: Next 16 официально поддерживает Safari ≥ 16.4, а ТЗ требует iOS 15+. Не проверялось.
- S3-драйвер и OAuth написаны, но с реальными Yandex и Google ни разу не запускались.
- Тяжёлая загрузка (50 устройств, 30 + 30 фото, 2 видео по 50 МБ по 4G) проверена только локально.

**Недоделки (некритично):**
- Нет фоновой очистки «осиротевших» файлов (загружены, но отчёт так и не отправлен) и протухших multipart-загрузок в S3 — настроить lifecycle-правило бакета для незавершённых загрузок или cron.
- `completeUpload`: если S3 завершил сборку, а запись в БД упала, повтор получит `NoSuchUpload` (редкий случай).
- Кэш `static-v1` в service worker не чистится от старых версий.
- В инструкциях `docs/` нет картинок (ТЗ просит для сотрудника). Скриншоты можно снять через `tests/e2e-report.mjs` (кладёт их в `tests/screens/`).
- Тайлы OpenStreetMap — бесплатные, но с политикой честного использования; при росте нагрузки перейти на Яндекс Карты (нужен ключ).

**Этапы 2–3 из ТЗ (не начаты):** сканирование штрихкода и QR серийника/MAC, дашборд аналитики, казахский язык (по решению заказчика), API для внешних систем.
